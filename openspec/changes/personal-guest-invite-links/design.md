## Context

The site is a Next.js 16 App Router app with `cacheComponents: true`. The whole invitation lives in `src/app/page.tsx`, content comes from `src/lib/wedding.ts`, and `src/components/RsvpForm.tsx` is a client form whose submit handler is a TODO. The Supabase project `ajbjgkvenmsnxirpodfg` exists and has no tables yet. The couple distributes links themselves through chat apps, email or printed QR cards. Guests are non-technical, so any friction such as logins or OTPs is a cost.

## Goals / Non-Goals

**Goals:**
- Only holders of a valid personal code can see the invitation details and RSVP.
- Guest data is never readable from the browser. All database access is server-side.
- RSVPs are persisted, tied to a guest, and capped at that guest's party size.
- The couple can import a guest list and get shareable links and QR codes with one command.
- A leaked link can be revoked or reissued without losing the guest's RSVP.

**Non-Goals:**
- Preventing a guest from forwarding their own link. This is impossible with links alone; the party-size cap limits the damage.
- An admin web dashboard. The Supabase Table Editor and the script cover this for now.
- Device locking, OTP, or Supabase Auth accounts for guests.
- Sending messages automatically. The couple sends the links.

## Decisions

### 1. Access model: unguessable code in the path, looked up on the server
`/i/[code]` with a 12-character URL-safe random code (72 bits of entropy, about 4.7×10²¹ possibilities). This is easier to share than a query string, and the path form survives chat apps that drop query parameters.
- *Alternatives:* a shared password (can't tell guests apart, no party cap); Supabase Auth magic links (too much friction for guests, and a session isn't needed); signed JWT links (stateless, but can't be revoked or tracked without a table anyway).

### 2. Code generated by a Postgres default
`code text not null unique default public.generate_invite_code()` uses `gen_random_bytes(9)` encoded as URL-safe base64 (12 characters). Rows added from the Supabase dashboard or the script get codes automatically, and there is one source of truth.
- *Alternative:* generate codes in Node. This works, but dashboard inserts would then need a manual code.

### 3. Server-only database access with the secret key; RLS on, no policies
Enable RLS on `guests` with no policies for `anon`/`authenticated`, and revoke table privileges from those roles. Next.js talks to Supabase only from Server Components and Server Actions through `@supabase/supabase-js`, using `SUPABASE_SECRET_KEY` from `src/lib/supabase.ts`, which is marked `import "server-only"`. The publishable key is never shipped, so the guest list can't be enumerated through the REST API.
- *Alternative:* public RLS policies plus an RPC `get_guest_by_code`. This is workable, but it exposes an API surface for no benefit because every read is already server-side.

### 4. Rendering with Cache Components
The `[code]` params are runtime data. The page sets `export const instant = false` and awaits params and the guest lookup at the top level, with no Suspense fallback, because there's no useful loading UI before the guest is verified. The guest lookup is **not** cached with `use cache`, so revocations and RSVP changes take effect immediately. The prerendered shell holds only the root layout. The whole invitation body, venue included, renders only after the code validates.
- *Status code trade-off:* the layout shell streams first, so invalid codes render `not-found.tsx` with HTTP 200 plus `noindex` (a "soft 404"). A true 404 would need a database lookup in Proxy on every request (per the Next 16 docs). That isn't worth it because the response reveals nothing.
- *Alternative:* the Suspense pattern with a loading fallback. It has the same status-code behaviour plus a visible loading flash.

### 5. Shared invitation component
Move the current `page.tsx` markup into `src/components/Invitation.tsx`, which takes `guest` as a prop for the greeting and the RSVP prefill. `/i/[code]` renders it. `/` renders a minimal "use your personal link" page with no venue or date details.

### 6. RSVP through a Server Action bound to the code
`submitRsvp(code, prevState, formData)` lives in `src/app/i/[code]/actions.ts`, and `RsvpForm` binds `code` to it. The action re-validates everything server-side:
- the code exists and is not revoked
- the RSVP deadline (`wedding.rsvpDeadline`, ISO) has not passed
- `attending ∈ {yes, no}`
- `1 ≤ guest_count ≤ party_size` when attending, and `guest_count = 0` when declining

Then it updates `attending`, `guest_count`, `message`, and `responded_at`. `RsvpForm` uses `useActionState` for pending, error, and success states. The guest-count select only offers `1..party_size`, and the form prefills existing answers so guests can change them.

### 7. Open tracking
On a successful lookup, set `opened_at = now()` where it is null, using `after()` so the update doesn't block rendering.

### 8. Link hygiene
`/i/*` pages set `robots: { index: false, follow: false }`. A `Referrer-Policy: no-referrer` header for `/i/:path*` in `next.config.ts` stops the code leaking to Google Maps and other outbound links.

### 9. Distribution script
`scripts/guests.mjs` runs with `node --env-file=.env.local`, so no TypeScript runner is needed. Subcommands:
- `import <file.csv>`: columns `name, party_size, phone?, email?, notes?`. It inserts rows and skips names that already exist.
- `export [outDir]`: writes `links.csv` (name, phone, email, party_size, url) and one QR PNG per guest to `invites/`, which is gitignored.
- `reissue <code>`: replaces the code, so the old link becomes invalid and the RSVP is kept.
- `revoke <code>` / `restore <code>`: toggles `revoked_at`.

Dependencies are `csv-parse` and `qrcode` (dev). The base URL comes from `NEXT_PUBLIC_SITE_URL`.

### Data model
```
guests
  id            uuid pk default gen_random_uuid()
  code          text unique not null default generate_invite_code()
  name          text not null              -- "Maria & Jose Santos"
  party_size    smallint not null default 1 check (party_size between 1 and 20)
  phone         text
  email         text
  notes         text                       -- private, never rendered
  attending     boolean                    -- null = no response yet
  guest_count   smallint check (guest_count >= 0 and guest_count <= party_size)
  message       text
  responded_at  timestamptz
  opened_at     timestamptz
  revoked_at    timestamptz
  created_at    timestamptz not null default now()
```

## Risks / Trade-offs

- [A guest forwards their link] → The party-size cap bounds the impact. `opened_at` and `reissue` let the couple react.
- [A code leaks through browser history or screenshots] → Revoke or reissue per guest. The Referrer-Policy prevents third-party leakage.
- [The secret key leaks to the client bundle] → Use `server-only` in `supabase.ts`, give the env var no `NEXT_PUBLIC_` prefix, and grep the build output before deploying.
- [Brute-force code guessing] → 72-bit codes make it infeasible. Rate limiting is out of scope.
- [Cache Components build errors from runtime params] → Wrap the lookup in Suspense as the docs prescribe, and verify with `next build`.
- [Guests RSVP after the deadline] → The form is replaced by a "contact the couple" message, and the server action rejects the request too.

## Migration Plan

4. Rollback: revert the commit to restore the public page. The table can stay.
